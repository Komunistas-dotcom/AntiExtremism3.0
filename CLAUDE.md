## 1. Что мы строим и зачем

Десктопное приложение под **Windows** для **самопроверки** собственных соцсетей и мессенджеров на следы взаимодействия с ресурсами из официального реестра экстремистских материалов. Пользователь запускает его на **своём** аккаунте (или раздаёт друзьям, которые запускают на своих). Цель — обнаружить и помочь удалить: **репосты / пересланное, подписки на признанные экстремистскими каналы и чаты, лайки, историю просмотров, ссылки в переписке/закладках**.

### Принципиальные ограничения (не нарушать)
- **Только свои данные.** Приложение работает с данными, к которым у пользователя есть легальный доступ (его логин / его экспорт данных). Оно НЕ предназначено для проверки чужих аккаунтов.
- **Local‑first / офлайн.** Ничего о том, «что пользователь лайкал/смотрел», не должно покидать машину. Никакой облачной телеметрии по содержимому. Это критично для чувствительности темы.
- **Не юридический продукт.** Приложение сообщает факты («найдено совпадение здесь»), а не даёт правовых оценок.

## 2. Источник данных — реестр

Файл: `spisok-ekstremistskix-materialov.md` — Республиканский список экстремистских материалов Республики Беларусь (решения судов, ст. 314 ГПК РБ). Это **справочный реестр**, а не пропаганда: перечень аккаунтов/каналов/чатов/групп/сайтов/книг/музыки.

Формат: одна большая **HTML‑таблица** (`<tr><td>…`), три колонки: тип материала / описание с идентификаторами / реквизиты судебного решения.

### Что важно для парсера реестра
- Идентификаторы приходят в разном виде: полные URL, `@handle`, короткие имена, **числовые ID** («идентификатор (ID), содержащий последовательность цифр …»).
- Часть Telegram‑чатов указана **только числовым ID без ссылки** → сопоставить по тексту ссылки нельзя, нужен доступ к API/экспорту аккаунта, видящему внутренние chat_id.
- Часть записей помечена **«Отменено»** → должны **исключаться** из активной проверки (но полезно хранить как «снятые»).
- Одна запись суда часто содержит **несколько «зеркал»** одного субъекта в разных сетях → нормализовать в связанные записи (one entity → many handles).
- Есть материалы **вне соцсетей**: книги/печатные издания, музыкальные композиции, логотипы/визуал, домены сайтов.

### Статистика по файлу (уникальные ресурсы, прибл.)

|---|---|---|---|---|

Приоритет реализации: **Telegram, Instagram, VK, Facebook, TikTok** (>90% объёма) → затем YouTube, OK, X → остальное вручную.

## 3. Ключевой инженерный вывод: как реально достаются следы

**Живой публичный API большинства платформ НЕ отдаёт чужие/свои лайки и историю просмотров.** Надёжный механизм — **официальный экспорт своих данных** (Download Your Data), который приложение парсит локально. Живой API пригоден только для **Telegram** и **VK** (свой аккаунт). Архитектура строится вокруг разбора архивов экспорта + 2 «живых» коннектора.

### Матрица следов (✅ надёжно · ⚠️ ограниченно · ❌ недоступно)
| Тип следа | Telegram | VK | Instagram | Facebook | TikTok | YouTube | X | OK |
|---|---|---|---|---|---|---|---|---|
| Репосты / пересланное | ✅ | ✅ | ⚠️ | ✅ | ✅ | ❌ | ✅ | ⚠️ |
| Подписки (каналы/чаты/группы) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Лайки | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ |
| История просмотров | ❌ | ❌ | ⚠️ | ⚠️ | ✅ | ✅ | ❌ | ❌ |
| Ссылки в переписке/сохранённом | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

Главное: **история просмотров** реально проверяема только в TikTok и YouTube; **лайки** — везде кроме Telegram (там их нет).

### Источник данных по платформам (что реализуют коннекторы)
- **Telegram** — **только защищённый вход по MTProto** (Telethon). Выгрузка Telegram Desktop **исключена решением от 2026‑07‑25**: она создаёт на диске архив со всей перепиской, который сам становится уликой. Живой вход даёт диалоги, подписки, пересылки, ссылки, «Избранное» — и главное, **внутренние числовые ID**. Лайков/реакций перечислить нельзя; истории просмотров нет.
- **VK** — API токена: `likes.getList`, `groups.get`, `wall.get`, `fave.get`; плюс архив «Загрузить копию своих данных». Просмотров нет.
- **Instagram + Facebook** — единый **Meta “Download Your Information”** (JSON/HTML): лайки, сохранённое, подписки, группы (FB), репосты/shares, комментарии, поиск. Через API недоступно.
- **TikTok** — Settings → **Download your data** (JSON): following, liked videos, **watch history**, favorites, search history, share history. Самый богатый экспорт.
- **YouTube** — **Google Takeout** (YouTube and YouTube Music): подписки, история просмотров/поиска, комментарии, плейлисты (вкл. «Понравившиеся»); доп. YouTube Data API v3.
- **X/Twitter** — Settings → **Download an archive of your data** (`like.js`, following, tweets/retweets, DM).
- **Одноклассники** — выгрузка данных в настройках + ограниченный API; **полнота истории «классов» требует эмпирической проверки** на реальном аккаунте перед обещаниями пользователю.
- **Viber / прочие** — экспорта подписок/лайков практически нет → кандидат на «полуручную проверку по подсказкам», не на автоматизацию.

```
                │              UI (Windows)                   │
                │   Мастер: выбор платформ → импорт → отчёт   │

              │                 │                              │
     ┌────────▼───────┐ ┌───────▼─────────┐          ┌─────────▼────────┐
     │ Экспорт-парсеры│ │ Живые коннекторы│          │ Локальные модули │
     │ (архивы DYI)   │ │ Telegram(TDLib) │          │ • история браузера│
     │ IG/FB/TikTok/  │ │ VK (API токен)  │          │ • файлы книг/муз. │
     │ YT/X/OK        │ │                 │          │ • (опц.) картинки │
     └────────┬───────┘ └───────┬─────────┘          └─────────┬────────┘
              │                 │                              │
              └─────────────────┴───────────┬──────────────────┘
                                             │  нормализованные «наблюдения»
                                  ┌──────────▼───────────┐
                                  │   Matching Engine     │
                                  │ индекс реестра ↔ следы │
                                  └──────────┬───────────┘
                                             │
                                  ┌──────────▼───────────┐
                                  │   Отчёт + экспорт     │
                                  │ где найдено / что делать│
                                  └──────────────────────┘
```

### Сквозные подсистемы (проектировать в первую очередь)
1. **Registry Normalizer** — реестр → единый индекс. Нормализация URL, `@handle`, коротких имён, числовых ID, `t.me/s/…`, редиректов, коротких ссылок; раскрытие «зеркал»; исключение «Отменено». Выход: таблицы `entities`, `identifiers(type, value_normalized, platform)`.
2. **Matching Engine** — вход: «наблюдения» пользователя (подписка/лайк/репост/ссылка/просмотр с платформой и raw‑идентификатором). Точное сопоставление по нормализованному значению + приблизительное (для опечаток/замен кириллица‑латиница, которых в реестре много). Числовые ID сопоставляются только с наблюдениями, где ID доступен (TDLib/VK).
3. **Report** — по каждому совпадению: платформа, тип следа, где именно (файл экспорта/диалог/раздел), исходная запись реестра (суд/дата), рекомендация действия. Экспорт отчёта в локальный файл; без отправки в сеть.
4. **Privacy layer** — всё офлайн; явное согласие; понятная модель хранения; лёгкая очистка импортированных данных.

## 5. Предлагаемый стек под Windows (на выбор — обсудить)
- **Вариант A (быстрый MVP, кроссплатформенный):** Python + парсеры (стандартный `json`, `csv`, `beautifulsoup4` для HTML‑реестра и HTML‑экспортов), матчинг на SQLite/FTS5, UI на **Tauri**‑подобной обёртке или простом desktop‑GUI. Упаковка в `.exe` (PyInstaller).
- **Вариант B (нативнее):** .NET (C#) + WPF/WinUI, SQLite; TDLib имеет .NET‑биндинги.
- Реестр и индекс — **SQLite** (одним файлом, удобно раздавать и обновлять).
- Telegram: **TDLib**; VK: HTTP API.

Критерий выбора не «язык», а: простота упаковки в подписанный `.exe` для раздачи друзьям + наличие MTProto‑библиотеки.

### Упаковка — зона ответственности пользователя
Пользователь собирает `.exe` сам через PyInstaller на своей машине. Claude отдаёт исходный код и, если нужно, называет список зависимостей — не более того.

Отсюда практическое требование к коду: **держать зависимости минимальными**. Сейчас всё ядро (реестр, сопоставление, браузеры) работает на чистой стандартной библиотеке; единственная сторонняя зависимость — `telethon` (плюс её `pyaes` и `rsa`), все чистый Python, нативных бинарников нет. Это свойство надо сохранять: любая новая зависимость с нативным кодом усложняет пользователю сборку.

## 9. Статус реализации: Веб-браузер и Телеграм

### Done

**Блок: Веб-браузер** (`connectors/browser.py`, `connectors/check_browser.py`, тесты `tests/test_browser.py`, `tests/make_browser.py`)
- Находит Chrome, Edge, Яндекс.Браузер, Opera, Brave, Vivaldi (движок Chromium, файл `History`/`Bookmarks`) и Firefox (`places.sqlite`) — **все профили каждого браузера**, не только `Default`.
- Читает историю посещений и закладки. Браузер держит базу открытой → читаем **временную копию** (включая `-wal`/`-shm` спутники), копия удаляется всегда, в т.ч. при ошибке.
- Повторные визиты на один адрес схлопываются в одно наблюдение с суммой посещений и датой последнего визита (иначе один сайт — десятки строк в отчёте).
- Ссылки на соцсети в истории/закладках (`t.me/...`, `instagram.com/...` и т.д.) распознаются наравне с сайтами реестра — идут через тот же нормализатор `registry.normalize`.
- Никакого API/авторизации не требуется — это чтение локальных файлов ОС. Авторизации нет и не нужно.
- Отчёт только на экране; сохранение на диск — по явному `--save`.
- Запуск: `python -m connectors.check_browser data/registry.db`.

**Блок: Телеграм** (`connectors/telegram.py`, `connectors/check_telegram.py`, тесты `tests/test_telegram.py`, `tests/fake_telegram.py`)
- Вход **только через MTProto** (библиотека `telethon`), выгрузка Telegram Desktop исключена решением от 2026‑07‑25 (сама создаёт архив-улику на диске).
- Сессия — `StringSession()` в памяти, файл сессии на диск не пишется. По завершении — **автоматический выход из аккаунта** (`client.log_out()`), чтобы не оставался чужой сеанс в «Устройствах». Отключается флагом `--keep-session`.
- Перед входом — явный текстовый CONSENT и вопрос согласия (`--yes` пропускает).
- Проверяются: подписки/каналы/чаты (с числовым chat_id — критично для 393 записей реестра без хендла), пересылки (`fwd_from`), ссылки в тексте и в скрытых `MessageEntityUrl`.
- **Читаются сообщения обеих сторон** (входящие и исходящие) — материал, присланный собеседником, тоже хранится в переписке пользователя и является следом. Разделены типы следов: `repost`/`link` (отправлено пользователем) vs `repost_received`/`link_received` (получено) — см. `matching/observation.py::TRACE_TYPES`, `RECEIVED_TRACE_TYPES`.
- Защита от анти-флуд ограничений Telegram: короткий `FloodWaitError` — ждём и продолжаем; долгий (> `max_flood_wait`, по умолчанию 60 с) — **останавливаем чтение сообщений** (подписки к этому моменту уже собраны) и сообщаем пользователю, не роняем сессию.
- Режимы: `--subscriptions-only` (без чтения сообщений), `--own-messages-only` (без чужих), `--quick` (только сообщения со ссылками через `InputMessagesFilterUrl`, без сплошного чтения), `--limit N` (сообщений на диалог, по умолчанию 3000).
- Зависимость `telethon` — чистый Python (+ `pyaes`, `rsa`), без нативных бинарников — совместимо с требованием §0/§5 про PyInstaller.
- Запуск: `python -m connectors.check_telegram data/registry.db --api-id ... --api-hash ...` (ключ с https://my.telegram.org).

### Architecture decisions

Общие паттерны, обязательные и для следующих блоков (VK, Meta, TikTok, YouTube, X, OK):

1. **Наблюдение (`Observation`)** — единый формат следа пользователя, независимо от источника. Поля: `platform`, `kind`, `value` (нормализованное значение), `trace_type` (см. словарь `TRACE_TYPES` в `matching/observation.py`), `source` (человекочитаемое "где нашли"), `raw`, `occurred_at`. Ключ для сравнения — `Observation.key` = `f"{platform}:{kind}:{value}"`.
2. **Один нормализатор на всех.** Наблюдения пользователя ВСЕГДА проходят через `registry.normalize` (те же функции `parse_url`, `normalize_host`, confusables-логику), что и записи реестра при сборке базы. Если завести отдельный нормализатор для нового источника — совпадения будут молча теряться. Для готовых URL — использовать `matching.observation.observe_url`/`observe_handle`/`observe_numeric_id`.
3. **Генератор, а не список.** Коннектор — это (по возможности async) генератор `Observation`, не накапливает переписку/данные в один большой объект без необходимости. Для источников без сети (браузер, файлы экспорта) — обычный `Iterator`.
4. **Разделение "разговор с источником" / "разбор в наблюдения".** В `telegram.py` это явно: `observations_from_dialog`, `observations_from_message` — чистые функции без сети, тестируются на поддельных объектах (см. `tests/fake_telegram.py`). Сетевая часть (`collect()`) — тонкая обвязка вокруг них. Для файловых источников (Meta/TikTok/YouTube JSON) аналогично: отдельно парсинг файла в объекты, отдельно превращение объекта в `Observation`.
5. **Приватность по умолчанию.** Ничего из данных пользователя не пишется на диск без явного действия (`--save`). Временные копии (как для браузера) удаляются всегда, включая ветку ошибки (`try/finally` или контекстный менеджер).
6. **Собственный вид следа для "отправлено vs получено"**, где это применимо (переписка, комментарии) — не схлопывать в один trace_type.
7. **Устойчивость к сбоям одного элемента.** Один битый файл/диалог/профиль не должен прерывать всю проверку — логировать в список ошибок и продолжать (см. `errors` в `TelegramCheckSettings`, try/except в `browser.read_history`).
8. **CLI-обвязка** (`check_<source>.py`) — принимает путь к `registry.db`, печатает прогресс, вызывает `MatchEngine.match_all()`, печатает `render()`, поддерживает `--save`. Единообразный интерфейс между источниками.
9. **Зависимости — только чистый Python, без нативных бинарников** (см. §5). Каждая новая зависимость проверяется на это перед добавлением.

### Not to touch

Без явного запроса не редактировать (блоки считаются завершёнными и покрыты тестами):
- `connectors/browser.py`, `connectors/check_browser.py`
- `connectors/telegram.py`, `connectors/check_telegram.py`
- `matching/observation.py`, `matching/engine.py`, `matching/report.py` — общий движок, от него зависят оба готовых блока
- `registry/*.py` — нормализатор и сборщик реестра, от него зависят все коннекторы
- `tests/test_browser.py`, `tests/test_telegram.py`, `tests/make_browser.py`, `tests/fake_telegram.py`, `tests/test_matching.py`

Если для нового блока требуется расширить `matching/observation.py` (например, новый `trace_type`) — это ожидаемо и разрешено, но менять существующие ключи/поведение уже определённых `trace_type` нельзя без явного запроса.

### Next

Оставшиеся источники по плану (см. §7, приоритет — по объёму реестра из §2):
1. **Meta (Instagram + Facebook)** — единый экспорт "Download Your Information" (JSON/HTML). Самый большой оставшийся кусок.
2. **TikTok** — "Download your data" (JSON): подписки, лайки, watch history, избранное, поиск, шеры.
3. **YouTube** — Google Takeout (YouTube and YouTube Music): подписки, история просмотров/поиска, плейлисты.
4. **VK** — живой API токена (`likes.getList`, `groups.get`, `wall.get`, `fave.get`) + архив выгрузки.
5. **X/Twitter** — архив выгрузки (`like.js`, following, tweets/retweets, DM).
6. **Одноклассники** — выгрузка + ограниченный API; требует эмпирической проверки полноты "классов" на реальном аккаунте.
7. **Viber / прочие** — экспорта нет, кандидат на ручную проверку по подсказкам, не на автоматизацию.
8. **Модуль файлов** (книги/музыка, ~140 записей реестра) — сопоставление по названию, не по идентификатору.
9. **UI-мастер** — выбор платформ → импорт → отчёт. Требует решения по GUI-стеку (Tkinter/веб-окно/Qt) — см. §0: сначала архитектура, потом код.
10. Упаковка в `.exe` — только после UI-мастера; делает пользователь сам (см. §5).
