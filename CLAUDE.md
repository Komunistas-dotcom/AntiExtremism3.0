## 1. Что мы строим и зачем

Десктопное приложение под **Windows** для **самопроверки** собственных соцсетей и мессенджеров на следы взаимодействия с ресурсами из официального реестра экстремистских материалов. Пользователь запускает его на **своём** аккаунте (или раздаёт друзьям, которые запускают на своих). Цель — обнаружить и помочь удалить: **репосты / пересланное, подписки на признанные экстремистскими каналы и чаты, лайки, историю просмотров, ссылки в переписке/закладках**.

### Принципиальные ограничения (не нарушать)
- **Только свои данные.** Приложение работает с данными, к которым у пользователя есть легальный доступ (его логин / его экспорт данных). Оно НЕ предназначено для проверки чужих аккаунтов.
- **Local‑first / офлайн.** Ничего о том, «что пользователь лайкал/смотрел», не должно покидать машину. Никакой облачной телеметрии по содержимому. Это критично для чувствительности темы.
- **Не юридический продукт.** Приложение сообщает факты («найдено совпадение здесь»), а не даёт правовых оценок.

## 2. Источник данных — реестр

Файл: `spisok-ekstremistskix-materialov.md` — Республиканский список экстремистских материалов Республики Беларусь (решения судов, ст. 314 ГПК РБ). Это **справочный реестр**, а не пропаганда: перечень аккаунтов/каналов/чатов/групп/сайтов/книг/музыки.

Формат: одна большая **HTML‑таблица** (`<tr><td>…`), три колонки: тип материала / описание с идентификаторами / реквизиты судебного решения.

### Что важно для парсера реестра
- Идентификаторы приходят в разном виде: полные URL, `@handle`, короткие имена, **числовые ID** («идентификатор (ID), содержащий последовательность цифр …»).
- Часть Telegram‑чатов указана **только числовым ID без ссылки** → сопоставить по тексту ссылки нельзя, нужен доступ к API/экспорту аккаунта, видящему внутренние chat_id.
- Часть записей помечена **«Отменено»** → должны **исключаться** из активной проверки (но полезно хранить как «снятые»).
- Одна запись суда часто содержит **несколько «зеркал»** одного субъекта в разных сетях → нормализовать в связанные записи (one entity → many handles).
- Есть материалы **вне соцсетей**: книги/печатные издания, музыкальные композиции, логотипы/визуал, домены сайтов.

### Статистика по файлу (уникальные ресурсы, прибл.)
| Платформа | Кол-во | | Платформа | Кол-во |
|---|---|---|---|---|
| Telegram (хендлы) | ~2100 | | YouTube | ~306 |

Приоритет реализации: **Telegram, Instagram, VK, Facebook, TikTok** (>90% объёма) → затем YouTube, OK, X → остальное вручную.

## 3. Ключевой инженерный вывод: как реально достаются следы

**Живой публичный API большинства платформ НЕ отдаёт чужие/свои лайки и историю просмотров.** Надёжный механизм — **официальный экспорт своих данных** (Download Your Data), который приложение парсит локально. Живой API пригоден только для **Telegram** и **VK** (свой аккаунт). Архитектура строится вокруг разбора архивов экспорта + 2 «живых» коннектора.

### Матрица следов (✅ надёжно · ⚠️ ограниченно · ❌ недоступно)
| Тип следа | Telegram | VK | Instagram | Facebook | TikTok | YouTube | X | OK |
|---|---|---|---|---|---|---|---|---|
| Репосты / пересланное | ✅ | ✅ | ⚠️ | ✅ | ✅ | ❌ | ✅ | ⚠️ |
| Подписки (каналы/чаты/группы) | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Лайки | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ |
| История просмотров | ❌ | ❌ | ⚠️ | ⚠️ | ✅ | ✅ | ❌ | ❌ |
| Ссылки в переписке/сохранённом | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

Главное: **история просмотров** реально проверяема только в TikTok и YouTube; **лайки** — везде кроме Telegram (там их нет).

### Источник данных по платформам (что реализуют коннекторы)
- **Telegram** — Telegram Desktop → Settings → Advanced → **Export Telegram Data** (JSON/HTML); либо **TDLib** (user API): диалоги, подписки, Saved Messages, поиск forwarded. Лайков нет; истории просмотров нет.
- **VK** — API токена: `likes.getList`, `groups.get`, `wall.get`, `fave.get`; плюс архив «Загрузить копию своих данных». Просмотров нет.
- **Instagram + Facebook** — единый **Meta “Download Your Information”** (JSON/HTML): лайки, сохранённое, подписки, группы (FB), репосты/shares, комментарии, поиск. Через API недоступно.
- **TikTok** — Settings → **Download your data** (JSON): following, liked videos, **watch history**, favorites, search history, share history. Самый богатый экспорт.
- **YouTube** — **Google Takeout** (YouTube and YouTube Music): подписки, история просмотров/поиска, комментарии, плейлисты (вкл. «Понравившиеся»); доп. YouTube Data API v3.
- **X/Twitter** — Settings → **Download an archive of your data** (`like.js`, following, tweets/retweets, DM).
- **Одноклассники** — выгрузка данных в настройках + ограниченный API; **полнота истории «классов» требует эмпирической проверки** на реальном аккаунте перед обещаниями пользователю.
- **Viber / прочие** — экспорта подписок/лайков практически нет → кандидат на «полуручную проверку по подсказкам», не на автоматизацию.

## 4. Архитектура (выбранное направление: гибрид)

```
                ┌────────────────────────────────────────────┐
                │              UI (Windows)                   │
                │   Мастер: выбор платформ → импорт → отчёт   │
                └───────────────┬────────────────────────────┘
                                │
              ┌─────────────────┼──────────────────────────────┐
              │                 │                              │
     ┌────────▼───────┐ ┌───────▼─────────┐          ┌─────────▼────────┐
     │ Экспорт-парсеры│ │ Живые коннекторы│          │ Локальные модули │
     │ (архивы DYI)   │ │ Telegram(TDLib) │          │ • история браузера│
     │ IG/FB/TikTok/  │ │ VK (API токен)  │          │ • файлы книг/муз. │
     │ YT/X/OK        │ │                 │          │ • (опц.) картинки │
     └────────┬───────┘ └───────┬─────────┘          └─────────┬────────┘
              │                 │                              │
              └─────────────────┴───────────┬──────────────────┘
                                             │  нормализованные «наблюдения»
                                  ┌──────────▼───────────┐
                                  │   Matching Engine     │
                                  │ индекс реестра ↔ следы │
                                  └──────────┬───────────┘
                                             │
                                  ┌──────────▼───────────┐
                                  │   Отчёт + экспорт     │
                                  │ где найдено / что делать│
                                  └──────────────────────┘
```

### Сквозные подсистемы (проектировать в первую очередь)
1. **Registry Normalizer** — реестр → единый индекс. Нормализация URL, `@handle`, коротких имён, числовых ID, `t.me/s/…`, редиректов, коротких ссылок; раскрытие «зеркал»; исключение «Отменено». Выход: таблицы `entities`, `identifiers(type, value_normalized, platform)`.
2. **Matching Engine** — вход: «наблюдения» пользователя (подписка/лайк/репост/ссылка/просмотр с платформой и raw‑идентификатором). Точное сопоставление по нормализованному значению + приблизительное (для опечаток/замен кириллица‑латиница, которых в реестре много). Числовые ID сопоставляются только с наблюдениями, где ID доступен (TDLib/VK).
3. **Report** — по каждому совпадению: платформа, тип следа, где именно (файл экспорта/диалог/раздел), исходная запись реестра (суд/дата), рекомендация действия. Экспорт отчёта в локальный файл; без отправки в сеть.
4. **Privacy layer** — всё офлайн; явное согласие; понятная модель хранения; лёгкая очистка импортированных данных.

## 5. Предлагаемый стек под Windows (на выбор — обсудить)
- **Вариант A (быстрый MVP, кроссплатформенный):** Python + парсеры (стандартный `json`, `csv`, `beautifulsoup4` для HTML‑реестра и HTML‑экспортов), матчинг на SQLite/FTS5, UI на **Tauri**‑подобной обёртке или простом desktop‑GUI. Упаковка в `.exe` (PyInstaller).
- **Вариант B (нативнее):** .NET (C#) + WPF/WinUI, SQLite; TDLib имеет .NET‑биндинги.
- Реестр и индекс — **SQLite** (одним файлом, удобно раздавать и обновлять).
- Telegram: **TDLib**; VK: HTTP API.

Критерий выбора не «язык», а: простота упаковки в подписанный `.exe` для раздачи друзьям + наличие TDLib‑биндингов.

2. Стратегия по **числовым Telegram‑ID без хендла**: только TDLib‑режим?
3. **Матчинг кириллица/латиница/диакритика** — в реестре много смешанных написаний; нужен нормализатор Unicode + confusables.
4. Модуль **истории браузера** (Chrome/Edge/Firefox — SQLite `History`) — сверка с ~315 доменами.
5. Модуль **картинок/логотипов** (~365) — тяжёлый (perceptual hashing, pHash); решить, нужен ли в MVP (скорее нет).
6. Обновление реестра: как доставлять новые версии списка друзьям (подписанный SQLite‑снапшот?).
7. Модель распространения: подпись `.exe`, автообновление, отсутствие ложных срабатываний антивирусов.

## 7. Порядок работ (черновик)
1. Registry Normalizer + парсер `spisok-ekstremistskix-materialov.md` → SQLite (с тестами на «зеркала», числовые ID, «Отменено»).
2. Matching Engine + отчёт (сначала на синтетических «наблюдениях»).
3. Первый коннектор — **Telegram** (самый объёмный): экспорт‑парсер, затем TDLib.
4. Экспорт‑парсеры Meta (IG+FB), TikTok, YouTube (Takeout), X, VK, OK.
5. Модули браузера/файлов.
6. UI‑мастер, упаковка, подпись.
